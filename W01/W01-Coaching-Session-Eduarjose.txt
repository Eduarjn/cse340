DEEPER DISCUSSION AND SELF-CORRECTION

AI Coach: Good work so far, Eduarjose. Before we go deeper, I want
to revisit something you mentioned in Topic 2. You described
import { fileURLToPath } from 'node:url' as destructuring. That is
a very common confusion, and it makes total sense - the syntax
looks almost identical.

But they are different language constructs. Real destructuring
would be something like const { dirname } = path, which happens at
runtime, on an object that already exists in memory. Whereas
import { fileURLToPath } is a named import: JavaScript resolves it
BEFORE the code runs, at compile time, by looking at what the
node:url module declares as its exports.

That difference has an interesting practical consequence.

Question: Knowing that import is resolved before the code executes,
what do you think would happen if you tried to write something like
this?

    const nomeDoModulo = 'node:url';
    import { fileURLToPath } from nomeDoModulo;

Would it work? And why?

Student: Very well observed! I really did confuse the two things
because of the identical syntax with the curly braces {}. The
difference between named import (compile time) and destructuring
(runtime) makes total sense. Thank you for the correction.

About your question: it would not work. Since the import is static
and resolved at compile time, the JavaScript engine requires the
module path to be a fixed string literal. If I try to use the
variable nomeDoModulo, JavaScript would only discover the value of
that variable at runtime, which is too late for the import
declaration. This would generate an error (SyntaxError). I know
that if we needed something like this at runtime, we would have to
use dynamic import with the import() function, and not the static
declaration at the top of the file.

AI Coach: Complete and precise answer. And you went beyond what I
asked - you brought up dynamic import() on your own, which is
exactly the correct way out when the module path is only known at
runtime. That shows you did not memorize the rule, you understood
the mechanism behind it. One fine detail: depending on the
environment, the error may appear during module parsing, before any
line executes at all - which reinforces your point that it is
"too late."

AI Coach: Let's go deeper into Topic 1, then. Looking at the end of
your server.js:

    app.get('/categories', (req, res) => {
      res.render('categories', { title: 'Service Project Categories' });
    });

    app.use((req, res) => {
      res.status(404).render('404', { title: 'Page Not Found' });
    });

That app.use() at the end has no path specified - it responds to
any request that reaches it. And it works: I tested your site on
Render and /pagina-inexistente returns 404 correctly, while
/categories returns 200.

Question: What would happen if you moved that app.use() block to
BEFORE your routes, right after express.static? Why does its
position in the file matter?

Student: If I moved that app.use() block to before my app.get
routes, the site would break. Any page I tried to access (like /,
/categories or /projects) would return the 404 page.

This happens because Express processes middlewares and routes
sequentially, exactly in the order they are written in the file
(from top to bottom). Since this app.use() has no path specified,
it acts as a wildcard and matches absolutely any request.

If it is at the top, it will intercept all requests, return the
res.status(404).render(...) and end the request-response cycle
right there. The request would never make it down to be evaluated
by the correct routes.

That is why the position matters a lot: the 404 handler must
necessarily be the last thing in the file. It works as a safety net
(catch-all) that only captures the request if it has fallen through
all the valid routes above it without matching any of them.

AI Coach: Exactly right. And you used an important expression:
"end the request-response cycle right there." That is the key to
the Express middleware model - what Express keeps internally is a
stack of functions, and each request travels down through it in
registration order.

That brings me to the piece you described without naming it. Notice
that your 404 handler receives only (req, res), but Express
middlewares can receive a third parameter:

    app.use((req, res, next) => {
      // ...
      next();
    });

Question: What is the role of that next, and why does it make sense
that your 404 handler is one of the few places where you do NOT
want to call it?

Student: The next() basically serves to pass the ball to the next
route or function in the Express queue. I don't use it in the 404
because the 404 is already the end of everything. Since I already
sent the error screen to the user there, the process is over. If I
put next() there, the server would try to keep processing the
request and it would break, giving that error of trying to send the
response (headers) twice.

AI Coach: That is correct, and well explained in your own words.
The error you are describing is exactly "Cannot set headers after
they are sent to the client" - Node raises it because the HTTP
response has already been committed and its headers can no longer
be modified. Your 404 closes the door, and that is precisely why it
does not call next().
